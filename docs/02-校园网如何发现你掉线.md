# 校园网是怎么发现你"掉线"的

> 上一篇把认证流程还原出来了。这一篇换个方向：**站在学校那侧看**——
> 它靠什么判断你掉线了、靠什么发现你一个账号在给多台设备用。
>
> 先说结论：这两个问题不是一回事，绝大多数人把它们混在一起，于是所有排查都跑偏了。

---

## 0. 先把两个问题分开

| 问题 | 学校在意的 | 你看到的现象 |
|---|---|---|
| **A. 你掉线了** | 这个 IP 上还有没有有效会话 | 网络突然不通，跳门户 |
| **B. 你在共享** | 这个 IP 背后是不是只有一台设备 | 认证成功但几分钟后又被踢；或限速、警告 |

A 是**会话管理**问题，B 是**指纹识别**问题。它们的技术手段完全不同，
而 A 里面还藏着一个第三者：

| | 真实情况 |
|---|---|
| **C. 你根本没掉线** | 是**你自己的探测或脚本**判定你掉线了，然后主动把活会话踢掉 |

第三类最反直觉，但它在我的实测数据里占了大头。先讲 A 和 B，最后用一整节讲 C。

---

## 1. A 层：会话是怎么被"回收"的

### 1.1 认证成功 ≠ 一直在线

Portal 认证的本质是：**在你这个 IP 和 BRAS（宽带远程接入服务器）之间建立一条会话记录**。

```
你的设备 ──► BRAS（记一条会话：IP / MAC / 账号 / 起始时间 / 用量）
              │
              └─► 放行到公网
```

认证成功只是"建立了这条记录"。记录之后会不会一直存在，取决于三件事：

1. **BRAS 的空闲/老化策略** —— 一段时间没有有效流量，回收；
2. **额度冲突** —— 同一账号新会话上线，挤掉旧会话（单点登录）；
3. **主动注销** —— 你自己（或你的脚本）调了下线接口。

第 3 条听起来荒谬，但它是最常见的原因。

### 1.2 怎么判断"真的被回收了"

只有一个可靠证据：**门户说这个 IP 上没有账号了**。

```
GET /portal/getOnlineUserName.do?wlanuserip=<你的IP>&wlanacname=<AC>&wlanacip=<NAS>

{"code":"2","message":"IP不在线"}                        ← 会话真没了
{"code":"0","data":"202500000000@DOMAIN"}                ← 会话还在
```

配合另一个接口交叉验证：

```
GET /portal/getRemoteAddr.do
{"code":0,"remoteAddr":"10.100.0.23"}                 ← 门户看到的你的源 IP
```

两个接口一组合，就能把"掉线"分成三类：

| 门户源 IP | 该 IP 上的账号 | 判定 |
|---|---|---|
| 有值 | **空** | **真·会话被清**（BRAS 回收 / 被顶号） |
| 有值 | **有值** | **假掉线**：会话还活着，是你的探测出了问题 |
| 空 / 超时 | — | 你连门户都到不了：本机链路或路由故障 |
| 源 IP ≠ 本机 WAN IP | — | IP 漂移：DHCP 换址导致会话失联 |

这张表是整个排查体系的骨架。**不看这张表就下结论，一定会误判。**

### 1.3 单点登录：那条让所有人困惑的提示

绕过所有技术细节，很多学校的门户前端里就写着一句话：

> 您的上次登陆，因被其他设备登陆账号，被踢下线。
> 请检查是否超出一台电脑一台手机的使用限制。

判定"电脑还是手机"的字段是 `accessTerminalType`：`'0'` 为电脑，其余为手机。

于是宿舍场景下必然发生：

```
宿舍墙上端口（判定为「电脑」）
   ├─ 路由器认证  → 占用唯一的「电脑」名额
   └─ 笔记本直连  → 也要占「电脑」名额 → 把路由器顶掉
                      路由器脚本再登回来 → 又把笔记本顶掉
                      → 无限拉锯，表现为"反复掉线"
```

这不是网络不稳定，是**两个设备在抢同一个名额**。

正确做法只有一个：**只让路由器认证，其余设备全部挂在它后面（LAN / Wi-Fi）**。
学校侧只会看到"1 台电脑在线"。如果必须让笔记本直连，就接受路由器被踢——两者只能选一个。

判断是不是这个原因，看登录返回的 `dropLogCheck`：

```
"dropLogCheck": "-1"    ← 主动重认证，不是被顶
"dropLogCheck": "1"     ← 被别的设备顶下线
```

一个字段就能定性，比看十张流量图有用。

### 1.4 一个被忽视的竞态：注销与登录之间

下线接口 `/quickauthdisconn.do` 的行为很反直觉：

```
调用 → 立刻返回 {"code":"0"}   ← 接口说"成功了"
      但 BRAS 侧会话真正断开要 6 秒以上
```

所以如果你（或脚本）的流程是：

```
disconn()   →  立刻  →  login()
```

就会出现：**新会话建好了，旧的注销动作才真正生效，把新会话一起带走了。**

表现为"刚认证成功就掉线，存活 30~60 秒"。这类问题的迷惑性在于：
日志上每一次操作都是"成功"的，只有把时间轴拉开看，才能发现是自己踩了自己。

**结论：会话还活着的时候，不要调 `disconn`。** 详见第 3 篇。

## 2. B 层：怎么发现"一个账号多台设备"

这层才是"防检测"的正题。学校不需要读你的设备列表，它只需要在**出口流量**上找矛盾。

### 2.1 信号一：TTL 跳数

不同操作系统的初始 TTL 是固定的：

| 系统 | 初始 TTL |
|---|---|
| Windows | 128 |
| Linux / Android | 64 |
| macOS / iOS | 64 |
| 部分网络设备 | 255 |

包每经过一个路由减 1。所以：

```
一台 Windows 直连校园网        → 出口 TTL = 128
一台 Windows 经路由器 NAT 出来 → 出口 TTL = 127（或更少）
一个宿舍同时有 Windows + iPhone → 出口同时出现 127 和 63
```

**同一个 IP 上同时出现 127 和 63，就是"一台 Windows + 一台手机"的铁证。**
这类判定不需要深度包检测，一个计数器就够。

### 2.2 信号二：HTTP User-Agent

明文 HTTP 请求里带着完整 UA 和 `Accept-Language`：

```
Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...      ← 电脑
Mozilla/5.0 (iPhone; CPU iPhone OS 17_0 like Mac OS X) ...  ← 手机
Mozilla/5.0 (Linux; Android 14; ...) ...           ← 安卓
```

同一 IP 上，三分钟内出现三种 UA，结论不言自明。

注意范围：**只对明文 HTTP 有效**。HTTPS 加密，UA 看不见——所以大部分检测发生在
你访问非 HTTPS 站点、或系统做连通性探测（`generate_204` 之类）的时候。

### 2.3 信号三：IPID 与 TCP 时间戳

- **IPID**：不同协议栈生成 IP 标识符的序列不同（有的全局递增，有的按连接随机）。
  同一 IP 上出现两套不同的递增规律 → 两台设备。
- **TCP 时间戳 / 时钟偏移**：不同设备的 `TSval` 起始值和增长速率有微小差异，
  长期观测可以聚类出"几个独立的时钟"。

这两个信号比 TTL 更隐蔽，也更难伪造，是商业"防私接"设备常用的手段。

### 2.4 信号四：连接数与会话特征

一个 IP 同时维持几十条到不同终端的长连接、且 TLS 指纹（JA3）多样，
也足以判定为"共享"。

### 2.5 自己动手观测这四个信号

在路由器 WAN 口抓，这是唯一能看到"出门后长什么样"的位置：

```bash
opkg install tcpdump

# 看 TTL / IPID（-v 会打印 ttl 和 id）
tcpdump -i wan -n -v -l -c 10 'tcp and dst port 80'

# 看 UA（明文 HTTP）
tcpdump -i wan -n -A -s0 -c 20 'tcp and dst port 80' | grep -i 'user-agent'
```

**最有力的一组对照实验**：同时在 LAN 口和 WAN 口抓同一个连接。

```bash
# 终端 1：LAN 侧（改写前）
tcpdump -i br-lan -n -v -c 4 'tcp and dst port 80'

# 终端 2：WAN 侧（改写后）
tcpdump -i wan -n -v -c 4 'tcp and dst port 80'
```

实测输出（Windows 客户端经路由器）：

```
① br-lan（改写前）:  ttl 128, id 10874, options [mss 1460,nop,wscale 8,nop,nop,sackOK]
② wan   （改写后）:  ttl 64,  id 17891, options [mss 1460,sackOK,wscale 9,eol]
```

TTL 从 128 归一化成 64，IPID 被重写，TCP 选项也被重建。
这就是"防检测"要达成的效果：**出口看起来像一台 Linux 设备，而不是一群设备。**

### 2.6 一个反直觉的前提：先关掉流卸载

如果你在 OpenWrt 上做 TTL 改写，却发现"规则加了但 ttl 还是 127"，八成是这个原因：

**flow offloading（流卸载 / Turbo ACC / 硬件加速）会让已建立的连接绕过 netfilter。**

前几个包走规则被改写了，后续包被卸载到硬件直通，改写全部失效。
所以做指纹归一化时，必须：

```
flow_offloading       = 0
flow_offloading_hw    = 0
```

代价是吞吐下降（MT7621 这类 SoC 上尤其明显）。这是"防检测"和"性能"之间的硬取舍，
没有两头都占的方案。

## 3. C 层：最常见的"掉线"，其实是你自己造成的

这一节是本文最有价值的部分，因为它推翻了我自己最初的结论。

### 3.1 最初的判断（错的）

第一天的数据是这样的：

```
07:49 掉线 → 08:10 掉线 → 08:31 掉线
间隔：20分35秒、20分47秒
```

三个样本，间隔高度接近 20 分半。加上"认证成功后没有任何周期性保活"这个事实，
一个非常自洽的假设就成型了：

> **BRAS 每 20 分钟回收一次空闲会话，因为我们缺保活。**

听起来无懈可击。于是准备上"每 18 分钟主动重认证"的方案。

### 3.2 第二天，统计口径变了

把一整天的日志全部拉出来重新分类，用 1.2 节那张表逐条判定：

| 类别 | 次数 | 判定依据 |
|---|---|---|
| A 真·会话被门户清空 | **9** | 门户源 IP 正常、账号为空 |
| B 假·会话还在但被脚本踢掉 | **13** | 门户源 IP 正常、**账号仍在** |
| C 无法判定（门户不可达） | **45** | 全部落在我折腾路由器的窗口内 |
| 合计 | **67** | |

**B 类 13 次**的成因，看代码就明白了：

```sh
# portal-login.sh 的重认证流程
diagnose()   # 只读诊断：此时门户显示账号还在（会话是活的）
disconn()    # ← 先调下线接口，把活着的会话主动杀掉
login()      # 再重新登录
```

而守护进程调用它时用了 `--force`：

```sh
OUT=$(sh "$LOGIN" --force 2>&1 | tail -3)
```

`--force` 跳过"在线就跳过"的判断。于是完整链路是：

```
本机 204 探测偶发失败（DNS 抖动 / 上游丢包 / 代理重启）
  → 守护连续 2 轮探不到 → 判定掉线
    → 调 portal-login.sh --force
      → 诊断显示：门户说账号还在（会话是活的）
        → 仍然 disconn + login   ← 把好会话踢掉，中断 15~25 秒
```

**本来什么都没发生，是脚本自己制造了一次掉线。** 而且 `disconn` 会清掉 BRAS 会话，
等于把会话寿命硬重置——所以它还会"制造"出新的 20 分钟周期，让那个错误假设看起来更可信。

### 3.3 更早的一次误判：101 次里 98 次不是学校的问题

再往前一天的复盘更极端。连续几小时每分钟掉一次，看起来像"被针对了"。
直到发现一个决定性证据：

```
那段时间，PC 连 192.168.1.1:22（局域网内的路由器 SSH）都连不上，失败 95 次。
```

**校园网掉线不可能让局域网内的 SSH 不通。** 问题必然在本机侧。

真实原因是：把透明代理从 REDIRECT 切成 TPROXY 后，代理进程把**路由器自身出站**的 TCP
也纳入了代理，形成环路——

```
3 秒写 12145 行日志 → CPU 49% → load 6.10 → 空闲内存 158MB 降到 28MB
→ 内核挂起 → 硬件看门狗复位 → 重启后 WAN 口无载波 16 分钟
```

那 16 分钟里，认证日志的 `ip=` 是空的——因为压根没有 IP。诊断记录显示"三次认证全失败"，
但这跟账号、跟学校没有任何关系。

同一天还有第二个陷阱：路由器重启后 RTC 未同步，日志时间比实际慢 6 分 21 秒。
如果不做时间校正，会把"重启"和"掉线"的因果关系排错顺序。

### 3.4 三个归因陷阱

| 陷阱 | 表现 | 后果 |
|---|---|---|
| **并发测试** | 排查时同时跑压测 / 另一个会话也在动路由器 | load 冲到 7.6，掉线归因完全不可靠 |
| **时钟未同步** | 重启后日志时间滞后数分钟 | 事件顺序错乱，因果倒置 |
| **观测空白** | cron 丢了、守护没起，夜里无人监测 | "连续在线 8 小时"其实是"8 小时没人看"，据此否定所有假设 |

第三条最阴险。我最初用"22:57 认证成功 → 次日 07:44 才掉线，连续在线 8 小时 48 分"
来证明"会话很稳定、不需要保活"。后来核对：那段时间守护 08:00 才上线，crontab 是空的，
日志里一条记录都没有。**这不是稳定，这是没人观测。**

### 3.5 正确的观测方法：四元组

任何一次"掉线"判定，都必须同时记录四个信号，缺一个就可能误判：

| 信号 | 命令 | 说明 |
|---|---|---|
| 数据面 | `curl -o /dev/null -w '%{http_code}' http://connect.rom.miui.com/generate_204` | 204 = 通 |
| 门户权威 | `getOnlineUserName.do` | 账号在不在 |
| 链路 | `cat /sys/class/net/wan/carrier` | 1 = 有载波 |
| 地址 | `ip -4 addr show wan` | 有没有 IP、有没有变 |

判定规则：

```
204 通                        → 在线（其余不用看）
204 不通 + 门户有账号          → 假掉线：本机探测/链路问题，不要认证
204 不通 + 门户账号空 + 有载波 → 真掉线：BRAS 回收或被顶，去认证
204 不通 + 门户不可达 + 无载波 → 本机链路故障，去修网线/驱动
```

这套逻辑直接决定了第 3 篇的守护设计：**探测失败不是认证的理由，"门户说没有会话"才是。**

### 3.6 修好之后的数据

改了两处（去掉 `--force`、认证前先做门户权威复核），上线后的观测：

```
14:07:12  认证成功
14:37     修复上线
15:01     仍未掉线 —— 已连续在线 54 分钟
期间      掉线事件累计 70 次，不变（0 次新增）
期间      204 探测零失败，门户权威查询全部 ONLINE
```

会话活了 54 分钟还没掉，直接否掉了"20 分钟硬超时"这个假设。

原来那三个 `20m25s / 20m57s / 23m14s` 的间隔，是**巧合**
（样本只有 3 个，且其中至少 1 次紧跟在人为 `--force` 之后）。

于是原定的四个方案全部作废：

| 方案 | 结论 |
|---|---|
| 每 18 分钟主动重认证 | **否决**：会话寿命远长于 20 分钟，主动踢自己等于凭空制造中断 |
| 探测缩到 5 秒 | **暂缓**：修好误判后探测误判已不致命，只加快真掉线恢复，收益小 |
| 周期保活接口 | **暂缓**：证据不支持它频繁发生，观察优先 |
| 复现官方客户端保活报文 | **不做**：前提尚未坐实，工作量最大 |

**这是本文最想传达的一点**：在根因没坐实之前加复杂度，等于用新 bug 掩盖旧 bug。

## 4. 一张图总结

```
你看到"掉线"
    │
    ├─ 局域网内也不通（SSH 都连不上）─────────► 本机故障，别怀疑学校
    │
    ├─ 门户有账号 ─────────────────────────────► 假掉线：你的探测错了
    │   └─ 而脚本还去 disconn ─────────────────► 自伤，最常见
    │
    ├─ 门户账号空 + 有载波 ────────────────────► 真掉线
    │   ├─ dropLogCheck=1 ─────────────────────► 被顶号（设备数超限）
    │   └─ 无此标记 ───────────────────────────► BRAS 回收 / 空闲超时
    │
    └─ 无载波 / 无 IP ─────────────────────────► 链路层：网线、驱动、PHY
```

顺带一句：如果你真正想解决的是"被识别为多设备"，那对应的是 2.1~2.4 那四个信号，
手段是 TTL/UA/IPID 归一化，跟"掉线"没有关系。**两个问题用两套手段，不要混着治。**
