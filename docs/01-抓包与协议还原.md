# 从零逆向校园网 Portal：抓包、读 JS、复现登录

> 本文目标：只用一个浏览器 + `curl` + `tcpdump`，把一个陌生校园网门户的认证流程完整还原成
> 一条可以脚本化的 HTTP 请求。全程不需要逆向二进制、不需要抓 HTTPS 明文。
>
> 文中域名、IP、账号、MAC 均为示例值，见 [README](../README.md#关于本文的示例数据)。

---

## 0. 这件事到底难在哪

校园网门户（深澜、锐捷、Dr.COM、GiWiFi 等）的认证请求长这样：

```
GET /quickauth.do?userid=...&passwd=...&wlanuserip=...&wlanacname=...
    &wlanacIp=...&vlan=...&mac=...&version=4&portalpageid=5
    &timestamp=...&uuid=...&hostname=...&bindOperatorType=2
```

二十多个参数。**其中一半不是你想填什么就填什么**：`wlanacname` 是 BRAS 的名字，`vlan` 是墙上端口
划的 VLAN，`timestamp` 和 `uuid` 由门户现签发，`portalpageid` 在配置接口里。猜是猜不出来的。

但它也不需要猜。因为**浏览器登录页自己就是答案**——前端 JS 会把这些参数一个一个拼出来，
再发给服务器。你要做的只是：

1. 让浏览器把登录过程跑一遍，看它发了什么；
2. 找到拼参数的那段 JS，看每个值从哪来；
3. 用 curl 复现一遍。

下面按这个顺序来。

---

## 1. 第一步：先认出"未认证"长什么样

这是全流程的突破口。没认证时的网络不是"断网"，而是**被劫持成一个只能看登录页的半开状态**。
认出这个状态，你就拿到了抓包的起点。

### 1.1 三个硬特征

插上网线（或连上校园 Wi-Fi）后，先不登录，直接测：

```bash
# ① 域名解析被劫持到假地址
nslookup www.baidu.com
#    → 超时 + 返回 3.3.3.3          ← 假地址，不是百度的真实 IP

# ② 但手动指定公共 DNS 就能正常解析
nslookup www.baidu.com 223.5.5.5
#    → 183.2.172.177                ← 说明劫持发生在学校的 DNS 上

# ③ 任意 HTTP 请求都被接走，返回门户跳转页
curl -i http://223.5.5.5/
#    → HTTP/1.0 200 OK
#    → <script>location.replace("https://portal.example.edu.cn/portal.do
#         ?wlanuserip=10.100.0.23&wlanacname=BRAS-01&mac=...
#         &vlan=100&hostname=...&rand=...&url=...")</script>
```

这三个特征合起来说明一件事：**你已经在二层/三层网络里了，只是没有被放行到公网**。
而那个跳转 URL 里，已经免费送给你四个关键参数：`wlanuserip`、`wlanacname`、`mac`、`vlan`。

> 记一条口诀，后面排查会一直用到：
>
> | 现象 | 含义 |
> |---|---|
> | ping 通网关 + 域名正常 + 网页正常 | 已认证，在线 |
> | ping 通 + 域名全解析到假地址 + 网页跳门户 | 通但未认证 |
> | 域名解析超时 / 全部 `000` | 链路或会话挂了 |
> | 跳转 URL 带 `dropLogCheck=1` | 被其他设备顶下线 |

### 1.2 为什么这条路比"直接抓 443"靠谱

有人第一反应是抓 HTTPS 解密。没必要，也不该做：

- 登录接口本身虽然是 HTTPS，但**跳转 URL 的 query 是明文的**，参数白送；
- **前端 JS 是明文的**，直接读源码就能看到拼参逻辑；
- 抓 HTTPS 需要中间人证书，涉及信任链改造，成本高且没有额外收益。

真正需要抓包的地方只有一个：**验证你发出去的报文到底长什么样**（尤其 TTL、UA 这类指纹），
那在第 2 篇讲。本篇的 90% 结论来自"读 JS + 看 query"，不是解密流量。

---

## 2. 第二步：三个抓包视角，各自回答不同问题

抓包工具用哪个不重要，重要的是**站在哪个位置看**。三个位置看到的东西完全不同。

### 视角 A：浏览器 DevTools（最快拿到参数）

`F12` → Network → 勾选 `Preserve log` → 在登录页输入账号密码 → 点登录。

找到那条 `quickauth.do`，看三样东西：

- **Request URL** —— 全部参数，直接复制；
- **Request Headers** —— `Referer`、`User-Agent`、`Cookie` 是否必需；
- **Initiator** —— 点进去直接跳到**发起这次请求的那行 JS**。

Initiator 是整篇文章最重要的一个按钮。它能让你从"看到结果"跳到"看到原因"。

### 视角 B：本机 tcpdump（确认报文真实形态）

DevTools 只告诉你"浏览器发了什么"，不告诉你"网卡上实际出去的是什么"。要看后者：

```bash
# Linux：抓 HTTP（802.1X / 门户劫持页都在 80 上）
sudo tcpdump -i eth0 -n -s0 -A 'tcp port 80' -w portal.pcap

# 只想看请求行和 Host，不落盘：
sudo tcpdump -i eth0 -n -A -s0 'tcp port 80' | grep -E '^(GET|POST|Host|User-Agent|Referer)'

# Windows：用 Wireshark 抓，过滤 http.request
```

抓 `80` 就够：登录接口虽然走 `443`，但**握手前的跳转、以及你被判定的指纹，都在明文里**。

### 视角 C：路由器 WAN 口（验证"出网那一跳"）

如果你打算把认证搬到路由器上（第 3 篇的内容），就必须站在 WAN 口看：

```bash
# OpenWrt / busybox 环境
opkg install tcpdump

# busybox 没有 timeout 命令，用 -c 限定包数代替
tcpdump -i wan -n -v -l -c 4 'tcp and dst port 80'
```

这一跳能看到本机看不到的东西：**TTL 被改成了多少、UA 变成了什么、IPID 是否连续**。
它是"防检测"类问题的唯一观测点，第 2 篇会详细展开。

## 3. 第三步：别猜参数，去读前端 JS

这是全篇的核心方法。登录参数不是协议规范定义的，是**这所学校的前端代码写死的**。
所以最权威的"协议文档"就是那个 `portalUtil.js`。

### 3.1 怎么定位到它

1. DevTools → Sources；
2. 或者直接从登录页 HTML 里找 `<script src="...">`；
3. 全文搜索这几个关键字：

| 搜索词 | 你会找到什么 |
|---|---|
| `quickauth.do` | 登录请求的拼参函数 |
| `checkOnlineInfo.do` | 登录前的在线额度检查 |
| `killOnline` | "踢掉某个在线设备"的函数 |
| `dropLogCheck` | "是否被顶下线"的标记 |
| `accessTerminalType` | 判定你是"电脑"还是"手机" |

### 3.2 一次真实的收获

在某高校门户的 `portalUtil.js` 里，有这样一段提示文案：

```
您的上次登陆，因被其他设备登陆账号，被踢下线。
请检查是否超出一台电脑一台手机的使用限制。
若怀疑账号被盗用，请及时通过自助系统修改密码。
```

同时 `accessTerminalType` 只有两种取值：`'0'` → 电脑，其余 → 手机。

**这两行直接解释了一个长期困扰的现象**：宿舍有线口被判定为「电脑」，路由器认证占掉那唯一的
电脑名额；此时如果笔记本再自己直连校园网，也判「电脑」——两边抢同一个名额，必然互相踢。

这个结论不是猜的，也不是从抓包里"感觉"出来的，是**前端代码写在那里的**。这就是读 JS 的性价比。

### 3.3 顺手把额度检查逻辑也读出来

```js
// 门户前端的真实逻辑（示意）
GET /portal/checkOnlineInfo.do?userid=..&passwd=..&other1=<dropMaxOnline>
if (code == "0") {
    if (data.type == 1) {                              // 有在线记录
        if (data.max > data.onlineList.length)         // 还有额度
            checkSubmit();                             //   → 直接登录
        else
            showCheckInfo();                           // 额度满 → 弹列表让你手动踢一个
    } else
        checkSubmit();                                 // 无记录 → 直接登录
}
```

再去看配置接口返回的 `checkOnlineFlag`，本例是 `0`：

> **登录前不查额度，直接提交** → 由 BRAS 侧判定超额，把旧的顶掉。

所以"我一登录，路由器就被踢"不是 bug，是配置决定的必然行为。**读懂这段，你就知道
"先踢后登"这条路径是被设计出来的，不要再试图用并发去抢。**

## 4. 第四步：参数溯源表

把 JS 里的拼参语句抄成一张表，逐项确认来源。这张表就是你的"协议文档"。

| 参数 | 示例值 | 来源 | 备注 |
|---|---|---|---|
| `userid` | `202500000000@DOMAIN` | 用户输入 | 有的学校是手机号，登录后门户内部 ID 会变 |
| `passwd` | 明文 | 用户输入 | 取决于 `authByRas`，见下 |
| `wlanuserip` | `10.100.0.23` | 本机 WAN IP | `ip -4 addr show wan` 动态读，别写死 |
| `wlanuseripv6` | 空 | — | 有 IPv6 的学校才填 |
| `wlanacname` | `BRAS-01` | 跳转 URL / `serverForm.servername` | BRAS 设备名 |
| `wlanacIp` | `10.20.16.2` | `serverForm.serverip` | 认证服务器地址 |
| `vlan` | `100` | 跳转 URL | 墙上端口划的 VLAN，各楼栋可能不同 |
| `mac` | `aa:bb:cc:00:11:22` | WAN 网卡 MAC | `/sys/class/net/wan/address` |
| `version` | `4` | `serverForm.portalVer` | 协议版本 |
| `portalpageid` | `5` | `portalconfig.id` | **注意：不是登录页 URL 里的数字** |
| `timestamp` | `1791387155974` | `PortalJsonAction.do` | 毫秒时间戳，每次现取 |
| `uuid` | `23c4b801-...` | `PortalJsonAction.do` | 每次现取，不能复用 |
| `hostname` | `DESKTOP-XXXXXXX` | 本机主机名 | 可以不伪装，但见第 2 篇 |
| `bindOperatorType` | `2` | 固定值 | 照抄 |
| `ssid` / `portaltype` / `validateCode` | 空 | — | 留空即可 |

**最容易错的两个**：`portalpageid` 和 `wlanacname`。前者是配置接口里的 `portalconfig.id`，
不是浏览器地址栏里的页面编号；后者要跟跳转 URL 里的一致，写错了会返回认证失败但不说原因。

## 5. 第五步：两步握手——先取配置，再登录

登录不是一步，是两步。因为 `timestamp` 和 `uuid` 必须由服务端现签发。

### 5.1 取配置

```
GET https://portal.example.edu.cn/PortalJsonAction.do
    ?wlanuserip=<ip>&wlanacname=<ac>&mac=<mac>&vlan=<vlan>
    &hostname=<hostname>&rand=<毫秒时间戳>&viewStatus=1
```

返回一段 JSON（本例约 2.2KB，**注意可能是 GBK 编码**）。从里面抠六个值：

```json
{
  "authByRas": false,
  "dropMacAuth": false,
  "portalconfig": {
    "id": 5,
    "tname": "xxx-pc-v2",
    "title": "电脑-单点登录",
    "checkOnlineFlag": 0
  },
  "serverForm": {
    "portalVer": 4,
    "serverip": "10.20.16.2",
    "servername": "BRAS-01"
  },
  "timestamp": 1791387155974,
  "uuid": "23c4b801-eb6c-4825-a5a3-a1287a078b52"
}
```

两个字段决定你的实现难度：

- **`authByRas = false`** → **密码明文传输**，不需要 RSA 加密。
  如果这里是 `true`，你就得找到前端公钥、复现加密，工作量翻几倍。
- **`checkOnlineFlag = 0`** → 登录前不查在线额度，直接提交。

### 5.2 再登录

```
GET https://portal.example.edu.cn/quickauth.do
    ?userid=...&passwd=...
    &wlanuserip=...&wlanuseripv6=&wlanacname=...&wlanacIp=...
    &ssid=&vlan=...&mac=...&version=4&portalpageid=5
    &validateCode=&timestamp=...&uuid=...&portaltype=
    &hostname=...&bindCtrlId=&validateType=&bindOperatorType=2
```

返回判定：

| 返回 | 含义 |
|---|---|
| `{"code":"0","message":"认证成功"}` | 成功 |
| `{"code":"7","message":"账号或密码不正确"}` | 账号或密码错 |
| `{"code":"2","message":"IP不在线"}` | 查在线状态时常见，正常 |

成功时还会带几个诊断字段，**一定要记进日志**：

```json
{
  "code": "0",
  "message": "认证成功",
  "dropLogCheck": "-1",     // -1 = 本次是主动重认证，不是被顶号
  "macChange": false,       // MAC 是否变化
  "groupId": 19             // 用户组，排障时有用
}
```

`dropLogCheck` 是最有价值的一个字段：如果它是 `1`，说明**上一次是被别的设备顶下去的**，
而不是超时或被回收。这一个字段就能把"掉线原因"分成两个完全不同的方向（见第 2 篇）。

## 6. 第六步：先用错密码验证接口

这条经验值得单独列一节，因为它能省掉大量反复踢自己的时间。

**不要一上来就用真密码试。** 先用一个假密码发一次请求：

```bash
curl -sk --noproxy '*' \
  "https://portal.example.edu.cn/quickauth.do?userid=202500000000@DOMAIN&passwd=wrongpw123&..." \
  --resolve portal.example.edu.cn:443:10.20.17.4
# → {"code":"7","message":"账号或密码不正确"}
```

拿到 `code:7`，说明**参数结构、域名、地址、路径、方法全部正确**，只是密码错。
这时再换上真密码，一次就通。

如果直接上真密码，返回的却是"认证失败"这种模糊错误，你没法区分是密码错还是参数错，
很容易反复重试——而**每次失败的登录尝试都可能把你自己正常的会话踢掉**。

## 7. 第七步：从"能跑通"到"能重放"

手工 curl 通了，离脚本还有四个坑：

### 7.1 `timestamp` / `uuid` 不能复用

每次认证前都要重新调一次 `PortalJsonAction.do`。用旧的会失败。

### 7.2 内网 DNS 可能解析不到门户域名

有些学校的门户域名只在认证前可解析，认证后反而 NXDOMAIN。用 `--resolve` 写死兜底：

```bash
curl --resolve portal.example.edu.cn:443:10.20.17.4 ...
```

门户外网 IP 可以从别的网络环境 `dig` 出来，或者从跳转页的 `Location` 里找。

### 7.3 本机代理会拦掉所有 curl

如果电脑上开着全局代理（Clash / 系统代理 / 公司 VPN），curl 默认会走代理：

- 不绑源地址 → 请求走代理，返回 `502`；
- 绑了源地址 → 代理连不上，`rc=7`（2ms 内失败）。

两种现象都会被误读成"网络不通"。**所有诊断性质的 curl 必须加 `--noproxy '*'`。**

### 7.4 编码

配置接口返回的 JSON 可能是 GBK。`sed` 抠字段没问题（ASCII 部分不受影响），
但如果要把 `title` 之类的字段打到日志，记得转码，否则会是乱码。

## 8. 完整的接口清单

把一次完整会话涉及的所有接口列出来，方便对照排查：

| 接口 | 方法 | 用途 | 是否必要 |
|---|---|---|---|
| `/portal.do` | GET | 登录页（跳转落地） | 观察用 |
| `/PortalJsonAction.do` | GET | **取配置**：timestamp / uuid / serverip / ver / id | 必要 |
| `/quickauth.do` | GET | **登录** | 必要 |
| `/quickauthdisconn.do` | POST | **主动下线**（踢指定 IP） | 慎用，见第 3 篇 |
| `/portal/getRemoteAddr.do` | GET | 门户看到的你的源 IP | 诊断用 |
| `/portal/getOnlineUserName.do` | GET | **该 IP 上登录的账号** | 诊断核心 |
| `/portal/checkOnlineInfo.do` | GET | 在线设备列表 / 额度 | 观察用 |
| `/portal/reauth.do` | POST | 重新认证 | 视学校而定 |
| `/portalLogout.do` | GET | SSO 下线跳转 | 观察用 |

其中 `/portal/getOnlineUserName.do` 是**整个诊断体系的地基**：
它返回"这个 IP 上现在有没有账号、是哪个账号"。

```
{"code":"0","message":"查询成功","data":"202500000000@DOMAIN"}   ← 有会话
{"code":"2","message":"IP不在线"}                                 ← 无会话
```

有了它，你才能回答"我到底是真的掉线了，还是只是自己探测失败"。
第 2、3 篇的所有判定，都建立在这个接口上。

## 9. 踩坑清单

| # | 坑 | 现象 | 处理 |
|---|---|---|---|
| 1 | 全局代理 | 全部 `502` 或 `rc=7` | 加 `--noproxy '*'` |
| 2 | 门户域名解析不到 | `Could not resolve host` | `--resolve host:443:IP` |
| 3 | 复用旧 timestamp/uuid | 认证失败，无明确原因 | 每次现取配置 |
| 4 | `portalpageid` 取错 | 认证失败 | 取 `portalconfig.id`，不是页面编号 |
| 5 | `wlanacname` 不一致 | 认证失败 | 以跳转 URL 为准 |
| 6 | 用真密码反复试 | 越试越掉线 | 先用错密码验证结构 |
| 7 | JSON 是 GBK | 中文乱码 | 转码后再解析 |
| 8 | 抓 443 想解密 | 全是密文 | 不需要，读 JS 即可 |
| 9 | 频繁 `disconn` 后立刻 `login` | 偶发"刚登录就掉" | 有 6 秒以上的竞态窗口，见第 2 篇 |

## 10. 合规边界（请务必读）

这套方法能跑通，前提是**你用的是自己的账号**。它的用途是"把自己已经拥有的上网权限自动化"，
不是获取权限之外的东西。

- **不要**用他人账号、不要绕过计费、不要突破学校设定的设备数限制去牟利；
- 学校对"一账号多设备"通常有明文规定，共享给室友前请先确认校规；
- 抓包只抓自己的流量；不要把含他人 MAC、账号的 pcap 公开；
- 本文所有域名、IP、账号、MAC 均为示例值，你需要在**自己的**环境里重新走一遍流程。

技术是中性的，边界在于使用者。下文第 2 篇讲检测机制，目的同样是**先理解，再决定要不要绕**——
很多时候理解了之后你会发现，真正的问题根本不是学校在踢你。
