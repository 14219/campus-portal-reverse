# 防掉线：守护进程怎么设计才不会自伤

> 前两篇解决了"怎么认证"和"怎么判断真的掉线"。这一篇把它做成一个能长期无人值守的东西。
>
> 核心结论只有一句：**探测失败不等于掉线。掉线的唯一判据是"门户说这个 IP 上没有会话"。**
> 本文剩下的内容，都是这句话的工程实现。

---

## 0. 先把目标写清楚

一个合格的校园网守护，应该满足四条硬指标：

| 指标 | 要求 | 为什么 |
|---|---|---|
| 恢复速度 | 真掉线后 < 30 秒恢复 | 视频会议/远程桌面能容忍的上限 |
| 误伤率 | 0 | **不能因为自己探测抖动，就把好会话踢了** |
| 自愈 | 进程崩溃、路由器重启后自动恢复 | 无人值守的前提 |
| 可观测 | 每次动作都有日志和判定依据 | 出问题能回答"当时为什么动了手" |

第三条和第四条是工程问题，第二条是**设计问题**——也是最容易做错的一条。

---

## 1. 架构演进：为什么不用 cron

最朴素的方案是"cron 每 2 分钟跑一次认证脚本"。它有三处硬伤：

| 问题 | 后果 |
|---|---|
| 最小粒度 60 秒 | 恢复慢，2 分钟轮询意味着最坏等 2 分钟 |
| **cron 会丢** | 实测中 `/etc/crontabs/root` 变成空文件，整夜无人守护，而日志里毫无痕迹 |
| 无状态 | 每次都是新进程，记不住"上次探测失败了几次"，只能一次定生死 |

于是改成**常驻守护 + procd 托管**：

```
┌─────────────────────────────────────────────┐
│ procd（开机自启 / 崩溃拉起）                  │
│   └─ portal-daemon.sh（15 秒循环）           │
│        ├─ 探测层：多个 204                      │
│        ├─ 判定层：连续失败计数 + 门户权威复核    │
│        └─ 执行层：调用 portal-login.sh          │
│                                              │
│ 兜底：                                                  │
│   ├─ hotplug：WAN up 立刻认证一次               │
│   └─ cron：每 5 分钟检查守护还活着没             │
└─────────────────────────────────────────────┘
```

三层各自解决一个问题：procd 解决"活不活"，hotplug 解决"开机/插网线后第一分钟"，
cron 解决"procd 也挂了"这种极端情况。

## 2. 探测层：为什么 204 在劫持网络里仍然可靠

探测用 `generate_204` 是常规做法，但有个前提需要证明：**未认证时门户会劫持 DNS，
那 204 探测不会误判成"在线"吗？**

不会。原理是：

```
未认证 → DNS 把域名解析到劫持地址（本例 3.3.3.3）
       → 该地址返回门户跳转页，HTTP 状态码 200
       → 不是 204
       → 所以"非 204"依然等价于"未认证/掉线"
```

关键是**劫持返回的是 200（门户页），不是 204**。所以哪怕域名全被劫持，判据依然成立。

但为了不依赖这一个假设，还是加一层：

```sh
probe() {
    for u in "http://connect.rom.miui.com/generate_204" \
             "http://www.gstatic.com/generate_204" \
             "http://connectivitycheck.gstatic.com/generate_204"; do
        c=$(curl -s -m 6 -o /dev/null -w '%{http_code}' "$u" 2>/dev/null)
        [ "$c" = "204" ] && return 0
    done
    return 1
}
```

三个地址分布在不同的 AS，避免"某一个域名被墙/被劫持"导致的单点误判。

## 3. 判定层：把"失败"升级为"掉线"之前，先问门户

这是整个设计的核心。逻辑是：

```
204 探测失败
   │
   ├─ 问门户：这个 IP 上还有账号吗？
   │     │
   │     ├─ 有 → 什么都没发生。记一笔"疑似误判"，累计计数
   │     │        └─ 连续 4 次（约 60 秒）仍失败 → 判定数据面异常 → 强制重认证一次
   │     │
   │     └─ 没有 → 真掉线 → 走认证流程
   │
   └─ 门户不可达 → 无法判定，等下一轮（不动作）
```

对应代码：

```sh
# 门户权威复核（只读，不改任何状态）
portal_online() {
    PORTAL_ON=""
    [ -z "$W_IP" ] && return 1
    r=$(curl -s -k -m 8 $RES -A "$UA" -e "https://$HOST/portal.do" \
         "https://$HOST/portal/getOnlineUserName.do?wlanuserip=$W_IP&wlanacname=$AC_NAME&mac=$W_MAC&wlanacip=$NAS_IP")
    case "$r" in
        *'"code":"0"'*'"data":"'*)
            d=$(printf '%s' "$r" | sed -n 's/.*"data"[[:space:]]*:[[:space:]]*"\([^"]*\)".*/\1/p')
            [ -n "$d" ] && { PORTAL_ON="$d"; return 0; } ;;
    esac
    return 1
}
```

调用处：

```sh
if probe; then
    rm -f "$SKIPF"; echo "ONLINE $(date +%s)" > "$STATE"; exit 0
else
    if [ "$MODE" != "--force" ] && portal_online; then
        SKIP=$((SKIP + 1)); echo "$SKIP" > "$SKIPF"
        log "⚠ 探测失败但门户报在线(账号=$PORTAL_ON) —— 疑似误判，跳过认证（连续第 ${SKIP} 次）"
        if [ "$SKIP" -lt 4 ]; then
            echo "OK $(date +%s) ip=$W_IP" > "$STATE"; exit 0
        fi
        log "🔁 连续 ${SKIP} 次探测失败但门户仍报在线 —— 判定数据面异常，强制重认证一次"
        rm -f "$SKIPF"
    fi
fi
```

### 3.1 一个细节：`code:0` 不够，还要 `data` 非空

最初的写法是"只要返回 `code:0` 就算在线"。这有个致命漏洞：

```
会话被清空，但门户接口本身可达
  → 返回 {"code":"0","message":"查询成功","data":""}
  → 旧逻辑判定"在线" → 永不重认证 → 真的掉线了却不管
```

所以判据必须是 `code:0` **且** `data` 非空：

```sh
case "$r" in
    *'"code":"0"'*'"data":"'*) ... ;;   # 两个都要匹配
esac
```

这个 bug 很隐蔽，因为它只在"会话刚被清、接口还通"的瞬间出现。

## 4. 执行层：两条不能碰的红线

### 红线一：不要 `--force`

```sh
# ❌ 旧写法（自伤的元凶）
OUT=$(sh "$LOGIN" --force 2>&1 | tail -3)

# ✅ 新写法
OUT=$(sh "$LOGIN" 2>&1 | tail -3)
```

`--force` 跳过脚本内部的"在线就跳过"判断。守护用 `--force`，
等于把第 3 节的整个判定层废掉——探测一抖，直接进入认证流程。

实测数据：一天 67 次掉线里，**13 次是这条引起的**。

### 红线二：会话活着时不要 `disconn`

```sh
# ❌ 认证前无条件先注销
disconn()
login()

# ✅ 只有确认会话已失效（门户账号为空）才走完整流程；
#    会话还在时，连认证都不该发起
```

原因见第 2 篇 1.4：`quickauthdisconn.do` 返回 `code:0` 之后，BRAS 侧真正断开还要 6 秒以上。
"注销 → 立刻登录"存在竞态窗口，会把刚建好的新会话一起带走，
表现为"认证成功后存活 30~60 秒又掉"。

如果确实需要"先踢后登"（比如换 IP 后旧会话残留），至少加 6 秒等待：

```sh
disconn()  # 只在判定需要时调用
sleep 8
login()
```

### 4.1 修复后的完整分支

```sh
wan_info                    # 先取 WAN IP/MAC（门户复核需要 W_IP）

if probe; then
    ONLINE
else
    if portal_online; then
        SKIP++                 # 疑似误判，累计
        [ $SKIP -lt 4 ] && exit 0
        FORCE_ONCE             # 连续 4 次才强制
    fi
    # 走到这里 = 门户确认没有会话 → 真掉线
    fetch_config
    disconn                    # 此时才允许注销
    login                      # 最多试 3 次
    verify                     # 复验门户在线
fi
```

注意 `verify` 那一步：登录返回 `code:0` 不等于真的通了。要再查一次门户，
确认该 IP 上确实出现了账号。**"接口说成功"和"网络真的通了"是两件事。**

## 5. 阈值：为什么是 4 次而不是 2 次

| 阈值 | 触发时间（15s 间隔） | 结果 |
|---|---|---|
| 2 次 | 约 30 秒 | 太敏感：一次 DNS 抖动 + 一次上游丢包就触发 |
| 4 次 | 约 60 秒 | 能过滤掉秒级抖动，同时真掉线的恢复时间可接受 |
| 10 次 | 约 150 秒 | 恢复太慢，视频会议已经断了 |

这里的取舍是**误伤率 vs 恢复速度**。因为加了门户复核，误伤的代价已经从
"踢掉好会话"降到"多问一次门户"，所以可以放心把阈值放宽到 4 次。

如果没做门户复核，2 次都嫌多——这就是为什么判定层必须先于阈值调优。

## 6. 开机与插网线：hotplug 补上第一分钟

procd 的守护是"启动后开始循环"，但开机到 WAN 拿到 IP 之间有一段空窗。
插拔网线、DHCP 续约失败重来，也会产生同样的空窗。

用 hotplug 在 WAN 接口 up 的瞬间触发一次认证：

```sh
# /etc/hotplug.d/iface/99-portal-autologin
[ "$ACTION" = "ifup" ] || exit 0
[ "$INTERFACE" = "wan" ] || exit 0
logger -t portal "WAN up，触发认证"
sleep 3                       # 等 DHCP 落定
sh /root/portal-login.sh >> /root/portal-hotplug.log 2>&1 &
```

`&` 放后台是必须的：hotplug 脚本是串行执行的，认证里的 curl 最坏要 20 秒，
会阻塞其它 hotplug 处理。

## 7. 看门狗与日志：让故障可见

### 7.1 procd 托管

```sh
# /etc/init.d/portal-daemon
#!/bin/sh /etc/rc.common
START=99
USE_PROCD=1

start_service() {
    procd_open_instance
    procd_set_param command /bin/sh /root/portal-daemon.sh
    procd_set_param respawn 3600 5 0     # 崩溃后 5 秒拉起，最多每小时 5 次
    procd_set_param stdout 1
    procd_set_param stderr 1
    procd_close_instance
}
```

### 7.2 cron 兜底

```cron
*/5 * * * * pgrep -f portal-daemon.sh >/dev/null || /etc/init.d/portal-daemon start
```

注意判断的是**进程在不在**，不是"网络通不通"。让两套机制各管一件事，
否则会互相干扰（watchdog 也在探测，就会重复触发认证）。

### 7.3 日志轮转

嵌入式设备 flash 小，日志必须有上限：

```sh
rotate_log() {
    [ -f "$LOG" ] || return 0
    n=$(wc -l < "$LOG" 2>/dev/null)
    [ -n "$n" ] && [ "$n" -gt 2000 ] && tail -1000 "$LOG" > "$LOG.tmp" && mv "$LOG.tmp" "$LOG"
}
```

### 7.4 日志里必须有的字段

每一条动作记录都要能回答"当时为什么动手"：

```
2026-10-08 14:37:12 诊断: 门户源IP=10.100.0.23 本机WAN=10.100.0.23 该IP账号=（空）
2026-10-08 14:37:13 ------- 掉线，开始认证 (dropLogCheck=无 mode=正常) -------
2026-10-08 14:37:14 门户参数: ip=10.100.0.23 ac=BRAS-01 vlan=100 ver=4 pageid=5
2026-10-08 14:37:15 ✅ 认证成功 (dropLogCheck=-1 macChange=false groupId=19)
2026-10-08 14:37:16 ✔ 复验通过: 门户显示该 IP 在线
```

其中 `mode=` 用来区分正常/强制，`dropLogCheck` 用来区分"被顶号"还是"自己重认证"。
少一个字段，事后复盘就少一条线索。

## 8. 配套：不做好指纹归一化，掉线会以另一种形式回来

如果学校侧判定"这个 IP 背后是多台设备"，它可能不是直接断你，而是：

- 缩短会话寿命，让你频繁掉线；
- 限速；
- 弹警告页。

所以"防掉线"和"防检测"是同一件事的两面。最小可用的配套是两条：

### 8.1 TTL 归一化（nftables）

```sh
# /etc/nftables.d/90-ttl.nft
table inet mangle {
    chain postrouting {
        type filter hook postrouting priority mangle; policy accept;
        ip ttl set 64
        ip6 hoplimit set 64
    }
}
```

前提：**必须关流卸载**，否则已建立的连接绕过 netfilter，规则形同虚设。

```sh
uci set firewall.@defaults[0].flow_offloading='0'
uci set firewall.@defaults[0].flow_offloading_hw='0'
uci commit firewall
/etc/init.d/firewall restart
```

验证方法（LAN 侧 vs WAN 侧对照）：

```sh
tcpdump -i br-lan -n -v -c 2 'tcp and dst port 80'   # 期望 ttl 128（Windows）
tcpdump -i wan    -n -v -c 2 'tcp and dst port 80'   # 期望 ttl 64
```

### 8.2 UA 改写：只用 REDIRECT

UA 改写工具（UA2F / UA3F 一类）有三种透明代理模式。
在 MT7621 这类弱 SoC 上，**只有 REDIRECT 是安全的**：

| 模式 | 结果 |
|---|---|
| **REDIRECT** | ✅ 稳定 |
| TPROXY | ❌ 把路由器自身出站也纳入代理，形成环路 → 看门狗复位 |
| NFQUEUE | ❌ 逐包送用户态，吞吐掉一个数量级；监听者卡死时直接黑洞 |

这两条不是理论推导，是实测踩出来的（见第 10 节）。

## 9. 验证清单

部署完别急着认为它好了，按这个顺序验：

```sh
# ① 语法
sh -n /root/portal-login.sh && sh -n /root/portal-daemon.sh

# ② 空跑：只探测 + 打印参数，不发认证请求
sh /root/portal-login.sh --dry-run

# ③ 单轮
sh /root/portal-daemon.sh --once

# ④ 在线时应"什么都不做"
#    关键：日志里出现"在线，跳过"，而不是"开始认证"
grep -c "在线，跳过" /root/portal-login.log

# ⑤ 模拟误判：把探测域名指向不可达地址后跑一次
#    期望：日志出现"疑似本机误判，跳过认证"，且掉线计数不增加
grep "疑似误判" /root/portal-login.log
grep -c "掉线，开始认证" /root/portal-login.log

# ⑥ 模拟真掉线：手动 logout，期望 30 秒内自动恢复

# ⑦ 长时间观测：204 + 门户 + carrier + WAN IP 四元组，至少 2 小时
```

第 ⑤ 步是最重要的回归测试。它验证的正是本文的核心命题：
**探测全失败时，只要门户说会话还在，脚本就不许动手。**

实测结果：

| 验证项 | 结果 |
|---|---|
| 探测全失败时的行为 | 输出"在线，无需处理"，日志"在线，跳过" |
| 是否产生"掉线，开始认证" | 没有（累计掉线事件数维持不变） |
| 会话是否被踢 | 没有，账号仍在线、204 探测正常 |

## 10. 三个反面教材

### 10.1 TPROXY 环路：3 秒写 12145 行日志

切到 TPROXY 后，代理进程建立了这样一条链：

```
自身出站 TCP → MARK 0x1c9 → ip rule fwmark 0x1c9 lookup 457
             → table 457 里 local default dev lo
             → 又回到自己
```

结果：

```
3 秒写 12145 行日志 → CPU 49% → load 6.10
→ 空闲内存 158MB 掉到 28MB → 内核挂起 → 硬件看门狗复位
```

复位后还有后遗症：WAN 口 PHY 卡在 `NO-CARRIER`，要 `ifdown wan; ifup wan` 才能恢复。

**教训**：透明代理必须把"本机自身出站"排除在外。任何"给自己发流量"的规则都是环路。

### 10.2 NFQUEUE 黑洞

```sh
-A POSTROUTING -p tcp -j NFQUEUE --queue-num 10301 --queue-bypass
```

`--queue-bypass` 只在"没有监听者"时放行。**它挡不住"监听者存在但卡死"**——
那种情况下报文排进队列后被丢弃。

症状：全网 `http=000`、SSH 超时、看起来像"彻底断网"，
但实际上链路、IP、路由全都正常。定位成本极高。

### 10.3 cron 丢失

某天发现 `/etc/crontabs/root` 是空的。没有报错、没有日志，只是守护没起来。

后果不只是"没有守护"，更严重的是**观测数据出现空白**，
而这个空白会被误读成"这段时间很稳定"（第 2 篇 3.4 节）。

**教训**：任何"定时任务"都要有独立的心跳检查。而且日志里要能看出"我在运行"，
不能让"没有坏消息"等同于"一切正常"。

## 11. 结果

修复上线后的实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 探测误判导致的踢会话 | 13 次/天 | 0 |
| 会话存活 | 10~44 分钟 | 54 分钟以上仍未掉（且非上限） |
| 掉线恢复 | 15~25 秒（但很多是自己造成的） | 真掉线 < 30 秒 |
| 观测噪声 | 每分钟都有事件 | 24 分钟零事件 |

这里最值得注意的不是"从 13 降到 0"，而是**修复的方式**：

没有加保活、没有缩短探测间隔、没有加重试——**只是把"什么时候该动手"这个判断修对了。**

大多数自动恢复系统的问题不在于"恢复得不够快"，而在于"不该恢复的时候恢复了"。

## 12. 这套设计的一般化

把第 3 节抽象出来，任何"自愈系统"都适用：

```
检测到异常（探测失败 / 健康检查不通过 / 心跳丢失）
   ↓
不要立刻执行恢复动作
   ↓
先用一个独立的、权威的信号源确认"异常是真的"
   ↓
确认是真的 → 执行恢复
确认是假的 → 记录一笔"疑似误判"，累计到阈值再考虑
无法确认 → 什么都不做，等下一轮
```

判断标准是：**你的动作有没有副作用？** 有副作用（踢会话、重启服务、切主备、删数据），
就必须先确认再动手。没副作用（只发个告警），随便。

本文的坑之所以值得写下来，是因为"探测失败就重连"这个写法看起来太自然了，
自然到没人会去质疑它——直到日志里出现"会话还活着，却被自己踢掉"。
